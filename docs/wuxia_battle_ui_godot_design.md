# 月下师门决斗战斗 UI 设计文档

> 当前 UI 管线总入口已迁移到 [UI_PIPELINE.md](UI_PIPELINE.md)，战斗规则入口为 [BATTLE.md](BATTLE.md)。本文保留为 UI 早期结构参考，标题、主题文案和部分入口链路可能已过时；若有冲突，以 `UI_PIPELINE.md`、`BATTLE.md` 和当前代码为准。
>
本文档记录当前视觉版 Godot 战斗 UI 的实际布局与交互规范，用于后续继续调整美术、动画、信息表达和代码结构。当前实现入口以 `MainVisual.tscn -> battle_controller_visual_ui.gd -> battle_controller_demo_visual.gd` 为准。

## 1. 当前目标

视觉版目标是提供一个可试玩、可观察、可快速迭代的横版武侠战斗界面。本文记录的“月下师门决斗”是旧版测试主题，当前剧情战斗不应在战斗场景顶部继续显示该字样。

当前 UI 必须优先保证：

- 战斗舞台、顶部 HUD、底部操作区、弹窗层级互不遮挡。
- 战斗区严格显示 9 个横向格位。
- 角色位置、朝向、攻击范围和意图预览能跟随当前局面刷新。
- 底部固定为三栏横排：招式区 1/2，详情区 1/4，效果预览区 1/4。
- 弹窗永远显示在最上层，不能被角色、格位、范围标记或意图气泡挡住。

## 2. 画面分区

当前画面按垂直方向分为三大区域：

- 顶部状态区：显示敌我头像、名字、门派、血量、势豆和中央标题。
- 中部战斗区：显示月下庭院背景、9 格站位、角色、意图气泡、攻击范围梯形。
- 底部操作区：显示操作按钮、招式牌、招式详情、效果预览。

关键边界：

- 战斗区背景只允许存在于中部舞台范围内。
- 底部 UI 有独立深色底板，不允许被背景、角色、格位、范围层侵入。
- 格位位置固定，角色可以微调落脚高度，但不能带动格位移动。

## 3. 当前节点层级

当前实现使用一个根 `Control`，按 z 层级管理前后关系。

```text
BattleControllerVisualUI (Control)
├── stage_layer (Control, z=-100)
│   ├── fallback background
│   ├── stage_scene_clip
│   │   └── moon_courtyard background
│   ├── stage_area_frame
│   ├── range_overlay_layer
│   ├── stage_grid_box
│   ├── stage_slot_label_box
│   ├── player_sprite / player_fallback_actor
│   ├── enemy_sprite / enemy_fallback_actor
│   ├── player_intent_bubble
│   ├── enemy_intent_bubble
│   └── center_fx_layer
├── top_hud (HBoxContainer, z=100)
│   ├── player_hud
│   ├── center_hud
│   └── enemy_hud
├── bottom_backdrop (PanelContainer, z=110)
├── bottom_root (VBoxContainer, z=120)
│   ├── control_bar
│   └── bottom_panels
│       ├── hand_panel
│       ├── card_detail_panel
│       └── effect_preview_panel
├── screen_flash (ColorRect, z=900)
├── overlay_scrim (ColorRect, z=1000)
└── overlay_panel (PanelContainer, z=1001)
```

层级规则：

- `stage_layer` 固定为底层，哪怕内部角色或意图气泡有较高 `z_index`，也不能盖住弹窗。
- `top_hud`、`bottom_backdrop`、`bottom_root` 是常规 UI 层。
- `overlay_scrim` 和 `overlay_panel` 是最高层。
- 每次打开弹窗时，需要对 `overlay_scrim` 和 `overlay_panel` 调用 `move_to_front()`。

## 4. 顶部状态区

顶部状态区采用左右对称布局：

- 左侧：玩家头像、角色名、门派名、血条、势豆。
- 中央：标题“师门决斗”和回合信息。
- 右侧：敌方头像、角色名、门派名、血条、势豆。

### 4.1 血量

当前血量用色条 + 数字展示，例如：

```text
24 / 24
```

血条刷新必须绑定真实 `fighter.hp / fighter.data.max_hp`。

### 4.2 势豆

势使用虚豆 / 实豆，而不是单个数字。

规则：

- 最大势决定豆子总数。
- 当前势对应实豆数量。
- 未充满部分显示虚豆。

当前回合规则：

- 从第 2 回合开始，敌我双方每回合开始各恢复 2 点势。
- 恢复值受最大势限制。

## 5. 中部战斗区

中部战斗区包含：

- 月下师门庭院背景。
- 9 个横向格位。
- 一位到九位标签。
- 敌我角色。
- 意图气泡。
- 逐格攻击范围梯形。

### 5.1 九格站位

格位固定为 9 个，从左到右：

```text
一位 二位 三位 四位 五位 六位 七位 八位 九位
```

当前格位参数：

- `GRID_SLOT_COUNT = 9`
- `GRID_SLOT_WIDTH = 126`
- `GRID_SLOT_HEIGHT = 48`
- `GRID_SLOT_GAP = 6`
- `GRID_STAGE_Y = 468`

格位位置不应随角色高度调整而变化。

### 5.2 角色位置

角色位置由格位中心和角色落脚线决定。当前角色落脚线略高于格位方形下缘：

- 格位底边约为 `GRID_STAGE_Y + GRID_SLOT_HEIGHT`
- 角色落脚线使用 `STAGE_GROUND_Y = 510`

设计意图：

- 角色视觉上站在格位区域附近。
- 人物底部略高于格位方形下缘。
- 不遮挡底部 UI。

角色贴图不再默认以图片中心定位。视觉层读取 actor meta 中的 `frame_size`、`foot_anchor`、`body_center` 和 `head_anchor`：

- 短武器角色继续使用 `512x512` 方帧。
- 长枪角色使用 `1024x512` 宽帧，容纳横刺和长枪杆。
- 战斗动作 sheet 统一使用 `1536x1536` 纵向三叠 PNG，actor meta 通过 `animations.*.file` 和 `sheet_layout=vertical` 裁切三帧。
- TextureRect 会按帧宽高动态设置显示盒。
- 格位对齐使用 `foot_anchor`，不是整张图片中心。
- 朝向翻转时同步镜像 foot anchor，避免长枪帧人物漂移。

### 5.3 角色朝向

当前角色 sprite sheet 默认朝右。视觉层必须动态判断朝向：

- 如果对手在右侧，角色朝右。
- 如果对手在左侧，角色朝左。
- 玩家穿身到敌人右侧后，玩家会自动转身朝左。
- 敌人穿到玩家左侧后，敌人会自动转身朝右。

真实贴图使用 `TextureRect.flip_h` 翻转。Fallback 占位角色使用负 `scale.x` 镜像，并补偿位置。

回合开始、选牌预览、静态站位刷新都必须使用同一套朝向逻辑。

## 6. 攻击范围展示

当前攻击范围不用整段连续大块，而是按每个被攻击格位逐格绘制梯形。

### 6.1 梯形规则

每一个攻击格显示一个独立梯形：

- 我方范围：蓝色半透明梯形。
- 敌方范围：红色半透明梯形。
- 重叠范围：不额外画金色框，仅由蓝红叠加自然表现。

梯形方向不能写死左右，必须根据施招者位置与攻击格位置判断：

- 施招者所在一侧为短边。
- 攻击延伸方向一侧为长边。
- 如果施招者在攻击格左侧，梯形左侧短、右侧长。
- 如果施招者在攻击格右侧，梯形右侧短、左侧长。

### 6.2 命中和范围符号

格位内文字只作为辅助：

- `·` 表示该格处于攻击范围。
- `×` 表示攻击范围覆盖到敌我角色所在格。

主要范围判断应看逐格梯形，而不是只看格子边框。

## 7. 意图气泡

意图气泡显示在角色正上方，随角色预期位置移动。气泡必须高于战斗角色和格位，但低于弹窗。

### 7.1 气泡文本格式

不要写“我方意图”或“敌方意图”前缀。直接写：

```text
位移｜招式名｜效果1｜效果2
```

示例：

```text
进1｜中平枪｜势-2｜伤害4
原地｜回圆架｜格挡4
退1｜探锋｜势+2
```

### 7.2 位移文本

位移以“面向对手”为参照：

- 朝对手移动 1 格：`进1`
- 朝对手移动 2 格：`进2`
- 背向对手移动 1 格：`退1`
- 背向对手移动 2 格：`退2`
- 不移动：`原地`

此逻辑必须根据当前双方相对位置动态判断，不能写死玩家向右或敌人向左。

### 7.3 效果文本

效果使用短格式：

- 格挡：`格挡10`
- 自身增势：`势+1`
- 削敌势：`势-1`
- 伤害：`伤害10`

多个效果按顺序用 `｜` 分隔。

## 8. 底部操作区

底部操作区固定为独立 UI 面板层，结构如下：

```text
bottom_root
├── control_bar
│   ├── 重选招式
│   ├── 确认出招
│   └── node_buttons_box
└── bottom_panels
	├── hand_panel
	├── card_detail_panel
	└── effect_preview_panel
```

### 8.1 三栏比例

底部三栏横向排列：

- 招式区：1/2 宽度，`size_flags_stretch_ratio = 2`
- 招式详情区：1/4 宽度，`size_flags_stretch_ratio = 1`
- 效果预览区：1/4 宽度，`size_flags_stretch_ratio = 1`

三栏之间必须有明确间距和边界，不能上下堆叠，不能互相侵入。

### 8.2 招式区

招式区显示本回合手牌：

- 卡牌按钮只承载简略信息。
- 选中后才在详情区显示完整说明。
- 横向超出时使用横向滚动，不允许撑开窗口导致下方不可见。

### 8.3 招式详情区

展示当前聚焦卡牌的静态说明：

- 招式名。
- 类型。
- 势消耗。
- 范围。
- 详细效果。
- 标签和 flavor text。

文字颜色要与底色保持足够对比。浅色纸面板使用深色文字。

### 8.4 效果预览区

展示当前局面下的动态预测：

- 当前选择的招式。
- 我方位置变化。
- 我方影响格位。
- 我方预计命中和伤害。
- 我方/敌方势变化。
- 敌方气血变化。
- 敌方可见意图及其预计效果。

玩家未选招时，按“不动”预览我方，并继续展示敌方可见意图和敌方招式效果。

## 9. 弹窗层

弹窗包括：

- 选择职业。
- 战斗摘要。
- 查看牌库。
- 合成藏招。
- 得招。

### 9.1 弹窗样式

当前视觉版弹窗采用浅纸色底板 + 深色文字：

- 标题使用深色文字。
- 正文使用深色文字。
- 按钮使用深色底 + 浅色字。

这样避免职业选择界面中“文字颜色和底色混在一起”的问题。

### 9.2 弹窗遮挡规则

弹窗必须位于最高层：

- 遮罩 `overlay_scrim`：`z_index = 1000`
- 面板 `overlay_panel`：`z_index = 1001`
- 打开弹窗时调用 `move_to_front()`

任何战斗层元素，包括角色、格位、攻击范围、意图气泡，都不能盖住弹窗。

### 9.3 选择职业界面

未选择职业前应隐藏无关战斗元素：

- 顶部 HUD 隐藏。
- 格位隐藏。
- 角色隐藏。
- 底部操作区隐藏。
- 节点按钮隐藏。
- 攻击范围层清空。

只保留背景、遮罩和职业选择弹窗。

## 10. 当前战斗规则相关 UI 绑定

### 10.1 敌方意图

敌方正式定招前，视觉层可以用 AI 生成“只读预览意图”：

- 不扣势。
- 不提交状态。
- 只用于气泡、范围和效果预览。

敌方藏招如果不可读，则显示可见表招；如果可读，显示实际招式。当前保留接口，识破逻辑未完全实现。

### 10.2 势与崩势

势相关 UI 需要跟随真实 Fighter 状态刷新。

当前规则：

- 每回合开始，敌我双方恢复 2 势。
- 非格挡且需要命中判定的效果，只有命中后才触发增势 / 削势。
- 削势把目标打到 0 时，目标进入下回合崩势。
- 崩势角色下回合无法行动。
- 崩势目标受伤翻倍。

## 12. 验收标准

当前视觉版验收以以下标准为准：

- 职业选择界面只显示必要弹窗，不显示无关战斗 UI。
- 弹窗永远盖住战斗层，不被角色或格位挡住。
- 顶部血量和势豆绑定真实数据。
- 敌我每回合开始恢复 2 势。
- 中部严格 9 格，标签从一位到九位完整。
- 角色底部略高于格位方形下缘，格位位置不移动。
- 角色始终面向对手，穿身换边后朝向自动反转。
- 攻击范围按格逐个显示梯形，短边在施招者一侧。
- 攻击范围重叠不使用额外金色框。
- 意图气泡显示短格式：位移 + 招式名 + 效果。
- 玩家未选招时按“不动”预览，并显示敌方可见意图及效果。
- 底部固定三栏：招式区 1/2，详情区 1/4，效果预览区 1/4。

## 13. 后续迭代建议

下一步可以继续优化：

- 把 `StatusPanel`、`MomentumDots`、`IntentBubble`、`SkillCardView` 拆成独立 scene。
- 将当前硬编码视觉参数整理成主题配置或 Resource。
- 增加真实立绘透明边缘清理和正式动作帧。
- 将预览逻辑进一步与真实结算共用同一套 resolver，减少 UI 预测与实战结算偏差。
